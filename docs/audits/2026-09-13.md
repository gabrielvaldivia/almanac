**1. Guard series operations against a missing ID — data-loss bug**

Editing a one-off event to repeat only changes its `repeatOption`; it neither creates occurrences nor assigns a `seriesID`. Reopen that event and the UI now offers Delete Series. The delete predicate compares optional IDs, so `nil == nil` matches every unrelated one-off event. The reproduction deleted both the selected event and an unrelated event. Bulk editing uses the same unsafe series selection.

Require a non-nil ID for every series operation and only show series actions for valid membership. Treat enabling repeat as an explicit conversion. Verify that unrelated event IDs survive both delete and edit operations. This is worth fixing immediately, independently of the larger recurrence redesign.

Source: [series deletion](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EditEventView.swift#L238), [repeat conversion and bulk selection](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EditEventView.swift#L335), [series action visibility](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EventForm.swift#L367).

**2. Stop truncating existing series on Save — data-loss bug**

The generator creates up to 365 occurrences. The editor only updates 99 occurrences on either side of the selected one, then **removes** the rest. Renaming the first event of a 365-event daily series reduced it to 100 events in the reproduction. No change to repeat frequency or end date was necessary.

Remove the deletion tied to the edit-loop counter. A scheduling/display limit must not delete stored events. Verify unchanged IDs and counts when only changing a title, category, color, or duration, including edits at the beginning, middle, and end of a long series.

Source: [future-event limit](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EditEventView.swift#L408), [past-event limit](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EditEventView.swift#L472).

**3. Fix category reorder and rename bookkeeping — data-corruption bug**

Entering Edit copies category names into a parallel array. Moving or deleting rows changes the category array without changing the copied names. On Done, the old names are written onto whichever category now occupies each index. Reordering Work and Social caused both test events to end up assigned to Social through successive renames.

Keep edits attached to category identity, or initially keep the draft array synchronized on every move/delete and apply renames from an immutable mapping. Validate unique, nonblank names: names currently serve as identities in several menus and event references. Rename/delete should also update the default category and any active filter. Deleting a category should explicitly reassign or clear its events' category, rather than leave an orphaned name.

Source: [draft commit](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/CategoriesView.swift#L185), [row mutations](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/CategoriesView.swift#L206), [name validation](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/CategoryForm.swift#L123).

**4. Replace the notification scheduler — known user-facing failure**

The earlier review found that daily summaries capture today's content and repeat it indefinitely, saving on an empty day cancels future daily coverage, and individual reminders subtract 15 minutes from a hidden event time. Individual requests also survive edits/deletions and are scheduled only for the first ten future records when enabling the toggle. Authorization is never requested or checked.

Create dated, nonrepeating summaries for actual event days at the selected local time. Reconcile pending requests after changes, remove obsolete requests, refill future coverage, and handle authorization. Account for the system's pending-request capacity and explain any practical scheduling horizon in the implementation. Remove the implicit 15-minute alerts unless they become a deliberate feature. Cover app-closed delivery, empty days, edits, midnight, daylight saving, and queue replenishment.

Source: [scheduler](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L450), [daily content and trigger](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L507). Apple's [local notification guide](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/SchedulingandHandlingLocalNotifications.html) explains repeating request delivery; its [authorization guide](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications) covers the missing permission flow.

**5. Preserve preferences — small fix, frequent benefit**

Initialization explicitly resets `defaultCategory` to an empty string and never restores it. Migration moves both default category and reminder time to the shared suite, while the app continues reading/writing standard defaults. The first such migration can therefore reset the reminder time to 8 a.m. Visiting Manage Categories also changes an intentionally empty default to the first category, so choosing None does not remain stable even within one session.

Choose one store for shared preferences, migrate once without losing values, load the saved default, and preserve None as a valid choice. Verify cold launch, visiting settings, renaming a default category, and changing notification time.

Source: [initialization](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L253), [migration](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L740), [Manage Categories side effect](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/CategoriesView.swift#L179).

**6. Honor the category used to open Add Event**

The Add button passes the current filter/default through `selectedCategory`, but the form saves `categoryOptions.selectedCategory`. When an incoming category exists, `onAppear` copies its color only. With Work selected and no default category, the resulting event is uncategorized and disappears from the Work view after saving. A conflicting default can be used instead.

Initialize one event draft from the incoming category, date, color, and other values. Avoid maintaining unused incoming bindings alongside independently initialized local state. Verify adding from a category filter and from the unfiltered screen.

Source: [incoming selection](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AddEventButton.swift#L44), [form initialization](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AddEventView.swift#L128), [saved category](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AddEventView.swift#L174).

**7. Make widget links work**

Widgets emit `upnext://addEvent`, `upnext://widgetTapped`, and `upnext://editWidget`. The **built app** registers only the old Google OAuth callback scheme. Opening `upnext://addEvent` on the fresh simulator failed with Launch Services error 115. Even after registration, the app only handles the `addEvent` host; the other routes carry no event ID or useful handling.

Register `upnext`, define supported routes, and pass an event ID when opening an event. Test both cold launch and an already-running app. Remove obsolete Google callback configuration if that integration is no longer planned.

**8. Validate repeat and date input**

Typing zero into Every is accepted and creates 365 copies on the same date. Negative/pasted values and very large After counts are also not bounded by the text fields; a Stepper's range does not validate a separate binding-backed text field. The generator has no requirement that the next occurrence advance. Separately, moving a start date beyond an existing end date can save an inverted range because start-date changes and Save do not validate that relationship.

Validate at the model boundary and in the form: interval at least one, a supported count limit, advancing recurrence dates, end date at or after start date, and a valid repeat end date. Clamp or clearly reject invalid edits. Keep calendar-day validation independent of the timestamp's hidden time.

Source: [Every input](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/RepeatOptions.swift#L73), [After input](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/RepeatOptions.swift#L159), [generation](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/Utilities.swift#L228), [start-date picker](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EventForm.swift#L117).

**9. Refresh both widgets after saves**

The central save path reloads `UpNextWidget` only. `NextEventWidget` has a different kind, so normal add/edit/delete operations can leave it showing an old or deleted event until WidgetKit next asks for its timeline. A few peripheral paths reload both, making this inconsistent.

Put widget invalidation in the single successful-save path and reload both affected kinds. Remove duplicate calls from views. Test add, edit, delete, and Delete All against both widget types. Apple's [`reloadTimelines(ofKind:)`](https://developer.apple.com/documentation/WidgetKit/WidgetCenter/reloadTimelines%28ofKind%3A%29) operates on the specified kind only.

**11. Make saved future events and history accessible**

If the only event is more than twelve months away, the app shows No upcoming events. View More exists only in the nonempty branch, so the user cannot expand the window to reach that saved event. An ongoing event spanning the whole window is also excluded because the filter checks whether either endpoint falls inside, instead of checking interval overlap.

**12. Do not overwrite a collection that failed to load**

One malformed event causes decoding of the entire array to fail. If the legacy fallback also fails, a fresh app instance stays empty and only logs the error. Adding an event afterward saves that nearly empty array over the original data. The reproduction demonstrated both the failed load and the destructive subsequent overwrite.

Track load failure separately from a genuinely empty collection. Preserve the original payload, keep a recoverable backup, and prevent normal writes until recovery is resolved. Decode older records with explicit version/default handling; consider recovering valid records individually. Verify malformed IDs, missing fields, old schema data, and interrupted recovery without modifying real user data.

Source: [load and fallback](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L337), [unconditional later persistence](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L435).

**13. Use one recurrence model for creation and editing**

Several independent rules disagree. Editing End Repeat does not persist `repeatUntil`, `repeatUntilCount`, or the selected end mode, and does not rebuild the occurrence count. Never is not stored as an explicit end mode: creation saves an artificial date and reopening infers On Date. Indefinite daily generation stops at 365 records without replenishment, while “until date” also stops after 365 occurrences even if the requested end is later. “After 3” stores an end date after the third generated event.

Monthly January 31 events drift through February 28 to March 28 because each recurrence is calculated from the previous clamped date. Bulk edits also use adjacent entries in the full event array rather than adjacent members of the series; a noncontiguous fixture took its next date from an unrelated December event. This last case is conditional on noncontiguous storage, rather than the usual freshly generated contiguous series.

Persist an explicit recurrence rule and derive occurrences through one function used by add/edit/refresh. Anchor month/year calculations to the original rule, define leap-day behavior, and preserve single-occurrence exceptions. Persist positive intervals and a clear end mode. Coordinate this with the safety guards in items 1–2 rather than waiting to protect existing data.

Source: [creation metadata](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AddEventView.swift#L162), [generator](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/Utilities.swift#L149), [end-date calculation](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/Utilities.swift#L307), [editor](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EditEventView.swift#L326), [reopened state](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EditEventView.swift#L516).

**14. Correct the timeline's geometry**

An event that started yesterday and continues tomorrow is included in the list but never drawn in the timeline: drawing requires its start date to exist in a range beginning today. Lane assignment counts earlier overlaps rather than finding an available lane. For A on days 1–3, B on 2–4, and C on 4–5, B and C both receive lane 1 and collide. A seven-day pill is 280 points wide while the seven columns occupy 304 points including spacing.

Clip ongoing events to the visible range, allocate lanes across the whole interval, and derive widths from the same column geometry. Use the same lane assignments for height calculation. Cache the date range/layout per input change; the current rendering repeatedly scans a year of dates and the event list. The geometry bugs are reproduced; the performance concern is structural and was not profiled under a large real dataset.

Source: [drawing gate](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/ContentView.swift#L104), [lane assignment](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/ContentView.swift#L141), [width](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/ContentView.swift#L172).

**15. Give Add Event proper accessibility behavior**

Replace the gesture-only action with a labeled Button and keep its visual feedback in a button style. **16. Align widget data and presentation**

The multi-event provider loads events once and reuses them for five hourly entries, including entries after midnight. Views use `Date()` rather than the entry's date and do not consistently remove newly past events. The Next Event provider uses timestamp comparison for an ongoing event's end, so it can omit an all-day event partway through its last day even while the app still includes it.

Widget bars also use category/default colors instead of the event's saved custom color. Category options are built in an unused static property; the String parameter has no options provider attached. Category matching is case-insensitive in the widget but case-sensitive in the app.

Build each entry relative to its entry date, schedule calendar-boundary entries, and share event inclusion/color rules. Attach category suggestions through a proper [DynamicOptionsProvider](https://developer.apple.com/documentation/appintents/dynamicoptionsprovider). Verify midnight, final-day events, custom colors, renamed categories, and category configuration. WidgetKit refresh requests are subject to system scheduling; see Apple's [timeline guidance](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date).

**17. Complete the subscription flow**

The app reads current entitlements once but does not listen to `Transaction.updates`. A pending purchase completed later can therefore leave the app state stale. Tapping Subscribe before product loading completes silently returns; loading/purchase errors only print to the console. Manage Subscription displays an instruction alert instead of opening management. An unused StoreKit 1 observer remains alongside StoreKit 2 code.

Use a lifecycle-owned StoreKit 2 listener, refresh entitlements deliberately, expose loading/error/pending states, and open subscription management. Test with the existing StoreKit configuration without making real purchases. No feature currently consults `isSubscribed` except the settings button, so clarify whether Pro is a supporter subscription or intended to unlock benefits; absence of gating is a product question, not automatically a defect.

Source: [entitlement read](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/Up_NextApp.swift#L25), [purchase implementation](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L624), [management button](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/SettingsView.swift#L162). Apple's [`Transaction.updates`](https://developer.apple.com/documentation/storekit/transaction/updates) documents the listener's role.

**18. Decide how all-day dates should behave when traveling**

The UI collects calendar dates, but storage records absolute timestamps using ISO 8601 and rendering interprets them in the current time zone. A September 14 midnight event created in New York becomes September 13 in Los Angeles. This shift was reproduced. The reminder-time preference is also a full Date rather than an explicit local hour/minute.

If these are floating all-day events, store date components or a date-only representation, and store reminder hour/minute separately. Define migration carefully because existing data does not record the original time zone. This is larger and riskier than fixing the known notification scheduler, and it should follow a decision about intended travel behavior.

Source: [event dates](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L15), [ISO persistence](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/AppData.swift#L435), [date-only input](https://github.com/gabrielvaldivia/almanac/blob/2d24e83/Up%20Next/Up%20Next/EventForm.swift#L437).

**19. Remove redundant and misleading code in small passes**

There are four Event definitions across `AppData.swift`, two `Models.swift` files, and `TimelineView.swift`. Only the AppData version is compiled into the shipping targets. `Shared/Models.swift`, `Shared/DateUtilities.swift`, the app's `Models.swift`, and `TimelineView.swift` are not target members; editing those apparent shared sources does not change the app. The old timeline even contains a second AppData definition.

Three active copies of the duration formatter exist in EventRow and the two widget views, plus unused alternatives. AddEventView and AppData have separate event-save paths. The two same-named encoding/decoding helper pairs use different date strategies, so consolidation needs compatibility checks rather than simple deletion. Redundant form state and manual `objectWillChange.send()` calls make ownership unclear; Event equality compares IDs only, so the explicit `onChange(of: events)` does not detect field-only changes.

The widget target includes category forms, repeat controls, the color picker, and all of AppData, including product loading, to obtain models and shared state. No shipping source imports either declared Google package, and both targets have empty package-product dependency lists, but Xcode still resolves the old packages and their transitive dependencies. The first build attempt was blocked by network resolution for those unused packages. The Live Activity is sample code displaying Hello/Leading/Trailing with no activity-start path. There are 52 print calls in app Swift files, including complete event dumps during generation and save.

First remove unused package references, sample features, dead helpers, and misleading unused files. Then establish one shared model/date layer and one save path, preserving schema compatibility. Restrict diagnostic logging and avoid dumping the entire event collection. Do not promote the alternate model files into the targets unchanged: their Codable behavior differs.
