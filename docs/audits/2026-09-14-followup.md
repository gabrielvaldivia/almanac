## Findings

### F01 — P1: Changing a recurrence ending deletes existing history

**Reproduce:** Retain a daily series beginning January 1, 2024. Change only its ending to January 1, 2030 and apply to the series. Previously stored 2024 occurrences disappear.

`updatingSeries` regenerates with the current date, using the generator's new-series history-skipping policy, then replaces every original member. Changing an ending should preserve historical occurrences that still belong to the schedule.

**Fix:** Separate materialization from series editing. Preserve surviving occurrence IDs, history, and exceptions; remove only occurrences excluded by the edited rule.

Source: [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 95–97, 217–228. Probe: `testEndingChangeDropsStoredHistory`. **Earlier finding, still open.**

### F02 — P1: Moving a monthly series produces dates inconsistent with its rule

**Reproduce:** Create January 31, February 28, and March 31, 2030 monthly occurrences. Move the first to January 30, applying to all. Stored dates become January 30, **February 27**, March 30; the updated rule says February **28**.

The unchanged-pattern branch shifts every occurrence by a fixed number of days. Month-end recurrence needs calendar-based recomputation from its anchor and occurrence index.

**Fix:** Recompute ordinary dates from the updated rule, preserving IDs and explicit exception semantics. Cover short months and leap-day yearly schedules.

Source: [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 188–204; [Models.swift](../../Up%20Next/Shared/Models.swift), `updatingLegacy`. Probe: `testMovingMonthlySeriesDisagreesWithRule`. **Earlier finding, still open.**

### F03 — P1: Deleting the only materialized occurrence erases an indefinite schedule

**Reproduce:** Create an indefinite event every two years beginning January 1, 2030. Only one occurrence exists within the materialization horizon. Delete “This Event.” Replenishing in 2032 produces nothing.

Rules and exclusion indices exist only on event records. Removing the last record removes the only copy of the schedule, even though the user did not delete the series.

**Fix:** Persist series definitions independently of their materialized occurrences. Store exclusions and exceptions by occurrence index; migrate existing embedded rules.

Source: [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 126–172. Probe: `testDeletingOnlyOccurrenceLosesFutureSchedule`. **Earlier finding, still open.**

### F04 — P2: “This Event Only” edits can leak into future occurrences

**Reproduce:** In the same every-two-years series, change the only stored occurrence's title and duration, choosing “This Event Only.” Replenishing the series copies both changes into the next occurrence.

When all stored records are exceptions, replenishment falls back to an exception as the template. The base title/color/category/duration are not stored independently.

**Fix:** Use a persistent series template and apply each exception only at its own index. This belongs with F03's model change.

Source: [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 106–118, 130–132, 158. Probe: `testSingleOccurrenceEditsLeakIntoFutureSparseOccurrences`.

### F05 — P2: “Show more” does not generate the next 365 days of recurrence

**Reproduce:** Create an indefinite daily series starting January 1, 2030. The first page contains 365 occurrences. Tap Show more: the second page receives only the one extra occurrence already stored at the original horizon, then the button disappears despite the series having no end.

The action only enlarges a date filter. Both its visibility and contents depend on already materialized records; recurrence generation remains limited to approximately one year from now. Existing pagination UI tests use preloaded one-off events, so they pass.

**Fix:** Let recurrence materialization accept a requested horizon. On pagination, append the requested range while preserving list identity/scroll position. Determine whether more pages exist from both stored events and recurring rules.

Source: [ContentView.swift](../../Up%20Next/Up%20Next/ContentView.swift), lines 371–381, 564–571; [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 87, 104. Probe: `testShowMoreExhaustsStoredDailyRecurrencesAfterOneExtraDay`.

### F06 — P2: The timeline can follow a row completely covered by its expanded header

**Reproduce:** Scroll from a quiet day through a group of four overlapping events to the following date. At the captured position, all four crowded cards are above the visible timeline bottom, yet the timeline remains on their September 29 date while October 14 is the first visible card.

The top-date preference checks `frame.maxY > 1`; it ignores the extra visible header height. With the native inset fixed at 104 points and the timeline expanded to 176 points, a hidden group still qualifies as the first visible group. The UI probe checks card frames against the actual timeline bottom and verifies the stale focused date.

**Fix:** Determine visibility using the actual overlay boundary (`headerOffset`) while keeping the native scroll inset stable. Do not undo the inset separation that fixed scrolling jumps.

Source: [ContentView.swift](../../Up%20Next/Up%20Next/ContentView.swift), lines 359–363, 604. Probe: `testInspectFocusWhileOverlayChangesHeight`. [Screenshot](2026-09-14-followup-assets/hidden-row-focus.png).

### F07 — P2: Invalid typed dates silently become Today, including beside valid recurrence

**Reproduce:** `Party 31 February`, `Party Sept 32`, and `Party Feb. 30` silently resolve to Today without schedule review. Adding a valid repeat phrase also hides invalid dates: `Party 2/30 every year` and `Party 31 February weekly` create a recurrence starting Today with the invalid date text left in the title.

The review regex recognizes fewer formats than the parser, and review is suppressed whenever any parse result exists. Parsing a valid repeat phrase therefore hides a failed start-date parse.

**Fix:** Return structured results for absent, valid, and invalid schedule components from one parser. Validate the date independently of whether recurrence parsed successfully.

Source: [NewEventDraft.swift](../../Up%20Next/Up%20Next/NewEventDraft.swift), lines 88–110; [QuickEventParser.swift](../../Up%20Next/Up%20Next/QuickEventParser.swift), lines 151–160. Probes: `testInvalidSupportedNamedDatesBecomeToday`, `testValidRecurrenceHidesAnInvalidStartDate`. **Earlier finding remains; recurrence variant is newly confirmed.**

### F08 — P2: Ordinary titles are blocked as invalid schedules

**Reproduce:** Enter `Until Dawn`, `Through the Looking Glass`, or `Every Breath You Take`. The unchanged title requires a repeat-setting correction even though it contains no schedule.

Any occurrence of `every`, `until`, `through`, or `starting` is treated as a recurrence hint when parsing returns nil.

**Fix:** Recognize plausible schedule syntax rather than isolated common words. Include title-only negatives alongside valid and invalid schedule tests.

Source: [NewEventDraft.swift](../../Up%20Next/Up%20Next/NewEventDraft.swift), lines 106–116. Probe: `testOrdinaryTitlesIncorrectlyRequireScheduleReview`.

### F09 — P2: Saving a valid historical date-limited series can add zero events

**Reproduce:** Configure a daily series from January 1–3, 2024. Validation accepts the dates, but `NewEventDraft.events` returns an empty array. Submission appends nothing, resets the draft, and emits success feedback.

The generator skips forward relative to now before checking the historical ending. The submission path treats an empty generated result as success.

**Fix:** Materialize the explicitly requested finite historical interval, and surface a failure if an otherwise valid creation request unexpectedly generates no events.

Source: [NewEventDraft.swift](../../Up%20Next/Up%20Next/NewEventDraft.swift), lines 58–61; [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 95–104; [ContentView.swift](../../Up%20Next/Up%20Next/ContentView.swift), lines 527–537. Probe: `testValidHistoricalDateLimitedSeriesCreatesNoEvents`.

### F10 — P2: Saving category metadata overwrites event color overrides

**Reproduce:** Set an event in blue Work to orange. Save Work without changing its color—even a no-op or keyword-only save—and the event becomes blue.

Every category save unconditionally assigns the category color to all matching events. This is broader than the previously reported rename-only case.

**Fix:** Separate category metadata changes from recoloring. Preserve explicit event overrides and distinguish inherited colors from overrides when changing a category color.

Source: [AppData.swift](../../Up%20Next/Up%20Next/AppData.swift), lines 299–310; [CategoriesView.swift](../../Up%20Next/Up%20Next/CategoriesView.swift), lines 82–89. Probe: `testCategoryMetadataSaveOverwritesColorOverride`. **Earlier finding, still open and expanded.**

### F11 — P2: Category rename/delete can break references during event-storage recovery

**Reproduce:** Enter event-storage recovery with an unreadable payload, rename Work to Career, then restore readable events. The restored events still reference Work, while only Career exists.

Category writes are guarded by category-storage health, whereas the related event write is independently blocked by event-storage recovery. The category change has already persisted when the dependent event save is refused. Deletion has the same split-write structure.

**Fix:** Block dependent category edits while events are unavailable; commit or roll back the category and event changes together.

Source: [CategoriesView.swift](../../Up%20Next/Up%20Next/CategoriesView.swift), lines 82–112; [CategoryForm.swift](../../Up%20Next/Up%20Next/CategoryForm.swift), Save validation; [AppData.swift](../../Up%20Next/Up%20Next/AppData.swift), line 213. Probe: `testCategoryRenameDuringRecoveryLeavesDanglingReference`. **Earlier finding, still open.**

### F12 — P2: Widget-generated future occurrences have unusable event links

**Reproduce:** Replenish the same stored yearly series independently for the widget and app after its stored horizon. The same future occurrence has a different UUID in each. Its Next Event widget URL cannot resolve in the app.

The widget generates without persisting, generation assigns random UUIDs, and the app resolves links only by event UUID. The probe confirms differing IDs for the same date; the URL handler establishes the no-op behavior. This audit did not physically tap a widget on a phone.

**Fix:** Use stable series/index identity for generated occurrences or deep links, preserving existing IDs during migration.

Source: [EventLoader.swift](../../Up%20Next/UpNextWidget/EventLoader.swift), lines 4–7; [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), line 107; [UpNextWidget.swift](../../Up%20Next/UpNextWidget/UpNextWidget.swift), Next Event link; [ContentView.swift](../../Up%20Next/Up%20Next/ContentView.swift), `handleOpenURL`. Probe: `testWidgetRefillsHaveUnresolvableIDs`. **Earlier finding, still open.**

### F13 — P2: Renaming a category breaks an existing widget filter

**Reproduce:** Configure a widget for Work, then rename Work to Career. The saved intent still filters by `Work`, and the renamed events no longer match.

**Fix:** Give categories stable IDs and migrate existing string-based widget configurations with an alias path. Define the fallback for deleted categories.

Source: [AppIntent.swift](../../Up%20Next/UpNextWidget/AppIntent.swift), category parameter; [WidgetEvents.swift](../../Up%20Next/Shared/WidgetEvents.swift), line 8. Probe: `testCategoryRenameEmptiesSavedWidgetFilter`. **Earlier finding, still open.**

### F14 — P2: Timeline Today uses a stale anchor after a time-zone change

**Reproduce:** Construct the timeline in New York, switch the process time zone to Los Angeles, update its events, then invoke Today. The focused date resolves to the previous local calendar day.

An absolute midnight anchor is retained for the lifetime of the view while later calculations use the current calendar/time zone. The update cache does not include calendar/day/time-zone changes.

**Fix:** Rebase and reindex on significant calendar/time changes while preserving the visible calendar date. Invalidate date-axis caches even when events have not changed.

Source: [EventTimelineView.swift](../../Up%20Next/Up%20Next/EventTimelineView.swift), lines 301, 394–411, 512–519. Probe: `testTimelineTodayDriftsAfterTimeZoneChange`. **Earlier finding, still open.** This reproduction concerns timeline focus, not proof of incorrect notification delivery.

### F15 — P2: Canceling Add Category clears the event's original category

**Reproduce:** Open an existing Work event, choose Category → Add Category, then Cancel. The parent editor now says None. Saving the parent persists that unintended removal; reopening confirms it.

The Add Category action clears the selection before presenting the sheet, and cancellation does not restore it.

**Fix:** Keep the current selection until a new category is successfully created and selected.

Source: [EventForm.swift](../../Up%20Next/Up%20Next/EventForm.swift), lines 234–237. UI probe: `testCancelingNewCategoryClearsExistingEventCategory`. [Screenshot](2026-09-14-followup-assets/category-cancel.png).

### F16 — P2: The full editor cannot commit its initially selected end date

**Reproduce:** Open a today event without an end date and tap End date. Today is already selected in the picker. Tapping it does nothing: the picker remains open and End date remains None. Selecting tomorrow commits and closes it.

Selection commits only in `onChange`, with no explicit confirmation action. The initially selected date cannot produce that change. A same-day end can be reached only by first selecting another day and then editing again.

**Fix:** Provide an explicit confirmation action or handle selecting the initial date, consistently with the quick date editor.

Source: [EventForm.swift](../../Up%20Next/Up%20Next/EventForm.swift), lines 354, 367–378. UI probe: `testFullEditorCannotCommitItsInitiallySelectedEndDate`. [Screenshot](2026-09-14-followup-assets/same-day-end.png).

### F17 — P2: Editing a large series blocks the main thread for seconds

For every member, the unchanged-pattern branch scans the entire original array with `events.first`. This makes a routine metadata edit quadratic. The operation is invoked synchronously from the editor; 10,000 occurrences is the supported repeat-count limit.

| Stored occurrences | Debug edit | Optimized Release edit | Release list grouping, for comparison |
|---|---:|---:|---:|
| 1,000 | 136 ms | 46 ms | 4 ms |
| 5,000 | 3.28 s | 1.11 s | 19 ms |
| 10,000 | 13.03 s | **4.35 s** | 37 ms |

These are single-run simulator measurements, not physical-phone benchmarks. Both the growth curve and the nested scan identify the expensive path; list grouping was much cheaper in this measurement.

**Fix:** Preindex original records by ID or preserve metadata during one traversal. Keep all-series operations responsive at the supported maximum and add a scaling/performance regression check.

Source: [Recurrence.swift](../../Up%20Next/Shared/Recurrence.swift), lines 197–200. Probe: `testMeasureLargeSeriesEditsAndListGrouping`.

### F18 — P2: Timeline event touch targets shrink to 6 points

Timeline event buttons have their visual marker bounds as their hit area: about 20 points in day view and 6 points when zoomed out. A point just one point outside the day marker fails hit testing; there is no expanded hit-area override. XCTest also flags the composer's 12-point-high collapse handle.

**Fix:** Preserve small visual marks while providing adequate effective touch areas and sensible overlap resolution; keep the list as an accessible alternative. Enlarge the collapse handle's interactive area without enlarging its visible line.

Source: [EventTimelineView.swift](../../Up%20Next/Up%20Next/EventTimelineView.swift), lines 578, 703–706, 737–752; [AddEventButton.swift](../../Up%20Next/Up%20Next/AddEventButton.swift), lines 62–69. Probe: `testTimelineMarkersHaveTinyHitTargets`; UI accessibility audit for the handle.

### F19 — P2: List text contrast and large-text support need correction

Apple's accessibility audit reports **failed contrast** on the blue date footnotes in the default light card style and borderline contrast on other labels. It also reports a partially unsupported Dynamic Type month heading and possible clipping of `IN 15 DAYS` at larger sizes. These are collected diagnostics, not a claim that every color/style combination fails.

The implementation uses category color at 70% opacity for small date text, retains a fixed 100-point relative-date column, and caps some editor scaling. The [normal-size screenshot](2026-09-14-followup-assets/normal-text-list.png) confirms the faint date text. At the largest accessibility size, [Today breaks across two lines](2026-09-14-followup-assets/large-text-list.png) and the narrow card column forces a long title into many lines. The composer's horizontally scrolling pills also occupy most of its width. This confirms poor reflow; the separate automated clipping warning is a diagnostic signal, not proof that offscreen text cannot be reached by scrolling.

**Fix:** Choose foreground colors for readable contrast independently of decorative category colors, including custom colors. Reflow the relative-date column and editor at accessibility sizes; verify the heading and calendar scale appropriately.

Source: [EventRow.swift](../../Up%20Next/Up%20Next/EventRow.swift), lines 54–75; [ContentView.swift](../../Up%20Next/Up%20Next/ContentView.swift), lines 596–608; [QuickDateEditor.swift](../../Up%20Next/Up%20Next/QuickDateEditor.swift), line 166. Evidence: `testCollectAccessibilityFindings` output and visual captures.

### F20 — P2: App and widget omit required-reason privacy declarations

There is no `PrivacyInfo.xcprivacy` in the source tree or either built Release bundle, while both targets use `UserDefaults`, including the shared app-group store.

Apple requires an approved reason declaration for this API category. Its current documentation lists app-group shared preferences under `UserDefaults` reason `1C8F.1`; the actual manifest must accurately cover all uses in each target. Sources: [Apple's required-reason API requirements](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api), [API categories and approved reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype).

**Fix:** Add appropriate manifests to the app and widget resources, verify their presence in an archive, and run App Store validation. The local compiler succeeding does not check this. No submission or rejection was performed during this audit.

Source: [AppPreferences.swift](../../Up%20Next/Shared/AppPreferences.swift), line 17; both targets' resource phases and built bundle contents.

### F21 — P2: Category corruption has a backup but no user-accessible recovery path

**Reproduce:** Save categories to create a readable backup, corrupt the active category payload, and retry loading. Editing remains paused on each retry despite `categories.lastReadableBackup` decoding successfully.

Events have a restore-backup method and Settings action. Category storage writes a backup too, but no category restore method/action consumes it; the error UI offers only Retry. Preserving corrupt data is appropriate, but the existing readable backup cannot be selected by the user.

**Fix:** Add explicit category-backup recovery with a reviewable warning and preserve the unreadable original. Validate restored category/event references together.

Source: [CategoryStorage.swift](../../Up%20Next/Shared/CategoryStorage.swift), lines 18–22; [AppData.swift](../../Up%20Next/Up%20Next/AppData.swift), lines 158–181; [CategoriesView.swift](../../Up%20Next/Up%20Next/CategoriesView.swift), lines 25–29. Probe: `testUnreadableCategoryHasBackupButNoAutomaticRecovery`; source review confirms the missing recovery action. Automatic recovery is not required to fix this.

### F22 — P3: Cross-year ranges omit the years

**Reproduce:** View a December 31, 2026–January 2, 2027 event during 2026. Its shared range description contains neither year. The decision to include a year uses only the start date, unlike the composer's separate policy.

**Fix:** Include year context when range endpoints cross years and share that policy between rows, widgets, and the composer.

Source: [EventDateText.swift](../../Up%20Next/Shared/EventDateText.swift), lines 6–10. Probe: `testCrossYearRangeOmitsYears`. **Earlier finding, still open.**

### F23 — P3: An existing list window loses its 365-day horizon after midnight

`EventListWindow` captures Today when created and resets only when the category filter changes. If the same view survives overnight, its end boundary is now 364 days ahead; subsequent days shorten it further. The model probe verifies the frozen boundary; the lifecycle path does not replace it on a day change.

**Fix:** Advance the page anchor on day/significant-time changes while preserving the visible row and previously loaded pages. Distinguish explicit history browsing from the forward pagination horizon.

Source: [EventSheetLayout.swift](../../Up%20Next/Up%20Next/EventSheetLayout.swift), lines 11–20; [ContentView.swift](../../Up%20Next/Up%20Next/ContentView.swift), lines 36, 306–307. Probe: `testPaginationBoundaryDoesNotAdvanceWithToday`.

## Rare boundary condition

An indefinite daily series whose last materialized records are approximately 30 years behind now fills only 10,000 old days in a single replenishment and still has no future occurrence. `fromIndex > 0` bypasses the new-series fast-forward logic while retaining the 10,000-iteration cap. Reproduced by `testRecurrenceAfterLongInactivityOnlyRefillsTenThousandOldDays`. This is a stress/legacy-data edge case, not a realistic 30-year absence for the current app; it is excluded from the 23 main findings. Address it when improving horizon-based materialization, with an explicit retention policy for gaps in history.

### Consolidation candidates

- **Widget grouping/sorting:** Medium and large layouts duplicate grouping, filtering, and sorting. Ordering currently converts relative labels back to numbers and treats day counts as seconds to produce sortable dates. That preserves basic ordering accidentally but is unnecessary; sort by dates and format afterward. The upcoming filter is also repeated between data preparation, rendering, and remaining-event counts.
- **Date parsing and validation:** The parser and partial hint regex implement overlapping grammars. F07/F08 demonstrate the maintenance cost; this should be consolidated as part of fixing behavior.
- **Date range formatting:** Row wrappers `getDurationText` → `rangeDescription` add little, and the composer maintains a different policy from the shared formatter. Consolidate with F22.
- **Editor initialization:** `EditEventView.setupInitialState` duplicates much of its initializer. Use one initialization policy so category/repeat/end-date defaults cannot drift.
- **Recurrence generation wrapper:** `Utilities.generateRepeatingEvents` delegates to `Recurrence`; its `showEndDate` parameter is unused. Its callers are active, so remove the redundant parameter/wrapper carefully rather than deleting the behavior.
- **Test-only layout helper:** `TimelineLayout.height(for:)` is only used by unit tests; shipping timeline height uses another calculation. Tests against that helper do not directly protect the rendered height. Test the actual layout policy or share one implementation.
- **Obsolete list modifiers:** `.listRowSeparator(.hidden)` on rows inside a plain ScrollView has no useful List effect.
- **Empty notification action branch:** The delegate's `VIEW_ACTION` branch does nothing and no matching action registration was found. Keep required delegate behavior, but remove the empty special case if it has no intended feature.
- **Terminology:** `EventSheet…` synchronization names remain after the draggable sheet was replaced by a list. Renaming is clarity work, not a product fix.

### Code requiring a compatibility or product decision

- **Subscription code:** `purchase`, `restorePurchases`, and `subscriptionPrice` have no product callers. However, product loading, entitlement refresh, and the transaction listener still execute in app lifecycle, and entitlement tests are active. The resulting state is not used by the visible product. This is an active but unconsumed subsystem, not wholly dead code. Decide whether subscriptions remain supported before removing lifecycle/entitlement handling for existing customers.
- **Legacy repeat flags:** `NewEventDraft.usesCustomRepeat` has no production reader; related `useCustomRepeatOptions` UI bindings are written/passed without a behavioral reader. `Event.useCustomRepeatOptions`, however, is persisted Codable data. Remove obsolete UI state separately from any schema migration; retain decoding compatibility where needed.
- **Serialization boilerplate:** Some manually implemented Codable behavior may be replaceable with synthesis, but old payload compatibility must be demonstrated before simplifying it. Do not delete fields based only on lack of visible UI use.

## Suggested implementation order

1. **Prevent loss and wrong schedules:** F01/F02, then the shared series-template/identity work for F03/F04/F12. Define migration and exception behavior before editing storage.
2. **Finish the current list behavior:** F05/F06/F23. Keep native scroll geometry stable, materialize each requested recurrence page, and use the real visible boundary for timeline focus.
3. **Make ordinary creation/editing reliable:** F07–F11 and F15/F16/F21; add desired-behavior regressions from the audit reproductions.
4. **Prepare a release:** F20, F17–F19, F13/F14/F22, then repeat a full app/widget build and user-flow checks.
5. **Clean up:** Remove high-confidence dead code in isolated changes. Consolidate overlapping date/widget policies alongside their fixes. Handle persisted fields and subscriptions separately.
